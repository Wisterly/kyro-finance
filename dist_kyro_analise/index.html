1. Resultado da Correção de Monotonicidade dos Fencing Tokens

Anteriormente, a liberação voluntária de um lease efetuava t.delete(leasePath), o que expurgava o documento do storage. Quando o mesmo titular (ou um novo processo) realizava uma nova aquisição posterior, o contador recomeçava em 1, quebrando a garantia formal de que o fencing token é estritamente monotônico crescente ao longo de todo o ciclo de vida do recurso.

Ajuste Arquitetural Implementado:

// src/engine/concurrency.ts -> releaseLease - t.delete(leasePath); + // Ao invés de apagar o documento e perder a sequência numérica, marca como liberado + // zerando titular e expiração, preservando a monotonicidade estrita do fencingToken para futuras reaquisições + const releasedRecord: LeaseRecord = { + ...existing, + holderId: '', + expiresAt: 0, + updatedAt: Date.now() + }; + t.set(leasePath, releasedRecord);

Tratamento na Reaquisição (`acquireLease`):

// Se existing possui holderId vazio ou expiresAt = 0, não é renovação de lease detido. // O sistema incrementa monotonicamente a partir do último token registrado no storage: + const nextToken = (existing?.fencingToken || 0) + 1; // Quando o lease foi liberado com token 2, a próxima reaquisição pelo mesmo titular recebe token 3!
